# 交接文档（重构版）：PI 扩展“模式优先”稳定化方案

> 目标仓库：`/home/h/projects/aiprojects/oh-my-opencode-slim`
>
> 本版用于替换旧的“workflow + message_end 改写”主导方案。
>
> 核心目标：在保持“指令遵循 / 降幻觉 / 降上下文污染”的前提下，显著降低系统复杂度与维护成本，避免再次进入“修一个崩一个”的循环。

---

## 0. 本次决策摘要（先看这个）

### 已确认方向
1. 采用**大删重建**，不再渐进修补。
2. 主路径从 `workflow` 切换为 **mode 优先**。
3. 保留 `mode + subagent` 最小内核，去掉高耦合链路。
4. 不再改写历史会话消息（session/history 只读）。
5. 不再依赖“提示词优先级文案”去约束提示词。
6. 约束改为 runtime 硬门：allowlist、完成态校验、伪执行拦截。
7. 扩展异常时，兜底流程就是：**禁用扩展并重启 pi**。

### 对旧方案的关键修正
- 旧文档中的 `message_end` 改写 finalized assistant message、reset 重写策略，判定为高风险，默认下线。
- `workflow` 不再承担日常质量控制主职责。
- fallback 不再承担工具恢复与魔法注入职责。

---

## 1. 为什么要改（系统性复盘）

### 1.1 真实问题不是“单点代码写错”
这轮故障表现（resume 崩溃、模式错乱、工具可用性漂移）显示：
- 问题跨越 mode / workflow / session / TUI 多层。
- 不是单个函数 bug，而是“高耦合系统 + 软约束执行”导致的连锁脆弱性。

### 1.2 复杂度与目标错配
本扩展最初希望解决：
- 指令不遵循
- 幻觉
- 输出质量不稳定

但采用的是：
- 多阶段 workflow
- 多层子代理编排
- 运行时消息改写
- 软提示词闭环

结果：
- 复杂度上升快于稳定性提升。
- 维护成本过高，回归频繁。

### 1.3 结论
当前阶段应从“能力堆叠”转为“稳定内核优先”：
- 先把系统收缩到可控边界。
- 再按硬约束逐步恢复必要能力。

---

## 2. 最小稳定内核（保留项）

以下为必须保留能力：

1. **Mode 切换内核**
   - `coordinator`
   - `fallback`

2. **Subagent 能力内核**
   - worker/oracle/fixer 等基本委托能力
   - delegates + tools 白名单约束

3. **工具权限硬约束**
   - allowlist 运行时生效
   - 非 allowlist 工具直接拦截

4. **基础对话执行链路**
   - 正常用户消息 -> agent 响应
   - 不依赖 workflow 才能完成任务

5. **Oracle 审查链路（保留）**
   - 章节结构检查保留
   - 同时加强证据有效性检查（测试/变更/风险）

---

## 3. 删除 / 下线项（第一阶段）

> 说明：先“逻辑下线”，验证稳定后再“物理删除”。

### 3.1 立即下线（默认关闭）
1. `workflow` 主路径入口（默认不走）
2. `message_end` 历史消息改写/替换逻辑
3. 运行时 session/history 修复或重写逻辑
4. fallback 的动态“全工具魔法注入”
5. 多层自动重试 / 自动纠偏 / 自动恢复链
6. 高风险复杂 `custom/custom_message` 渲染路径（先降级）

### 3.2 后续物理删除
在第一阶段稳定后，删除：
- workflow 命令入口
- workflow 状态机主链（保留归档 tag）
- workflow 事件桥接及相关冗余测试

---

## 4. Fallback 规则（详细定义，避免歧义）

### 4.1 Fallback 的职责（保留）
- 作为“直接干活模式”（无 workflow 依赖）。
- 提供稳定、可预期的基础执行能力。

### 4.2 Fallback 不再承担（删除）
- 不做工具恢复职责。
- 不做“根据当前状态猜测全工具”的魔法注入。
- 不继承上个 mode 的工具集。

### 4.3 Fallback 改为静态 preset
- 使用固定工具清单（配置可见、可测试、可复现）。
- 切换到 fallback 时仅执行：
  1) 写 currentMode
  2) 应用 fallback preset
  3) 写 mode-change 事件
- 应用失败：立即显式报错，不二次补偿。

---

## 5. Mode 切换契约（系统状态，不靠模型理解）

> 关键原则：mode 切换是 runtime 状态同步，不是“提示模型后期待它自觉”。

每次 mode 切换成功后，系统必须原子完成：
1. `currentMode` 更新
2. `allowedTools` 更新（来自静态 preset）
3. `turnExecutionContext` 重置（当前回合执行态清零）
4. 记录 mode-change 事件（供观测）

### 5.1 新会话启动一致性
新会话第一轮前强制初始化：
- currentMode
- currentAllowedTools

禁止：
- 从历史 tool call/tool result 反推当前工具集。
- 从历史模式消息推断 mode。

### 5.2 首轮健康检查
若出现以下任一情况，直接失败并提示：
- mode 存在但 allowedTools 为空
- allowedTools 有重复项
- allowedTools 含未知工具名

---

## 6. 指令遵循 / 幻觉 / 上下文污染：硬约束化

> 用户已明确：不采用“提示词优先于提示词”的文案约束。

### 6.1 提示词层定位（降级）
提示词只做任务语义说明，不做强控制。

### 6.2 强控制全部下沉 runtime
1. **工具调用硬门**
   - 非 allowlist 工具：拒绝执行
2. **伪执行硬门**
   - 声称执行但无工具调用证据：拦截/要求重答
3. **完成态硬门**
   - 未通过最小验收，不可进入 completed/continue
4. **输出结构硬门**
   - 使用机器可校验最小字段，缺失直接 reject

### 6.3 Oracle 审查策略（保留并增强）
- 保留章节结构检查（满足规范约束目标）
- 增加证据有效性检查（防“有标题没内容”）
- 结论继续走审批门，不自动放行

---

## 7. 上下文策略（只控窗口，不改历史）

### 7.1 禁止事项
- 禁止运行时改写历史 session/message。
- 禁止“删旧模式提示词并重写历史工具结果”为主策略。

### 7.2 允许事项
- 当前窗口摘要化 / 滑窗裁剪。
- 将历史工具结果提炼成短结论（用于当前轮），但不回写原 history。

### 7.3 原因
- 历史是多消费者真相源（resume/TUI/统计都依赖）
- 改历史会放大兼容性与恢复风险

---

## 8. Workflow 模块处置策略

> 结论：不立即物理删除，先停主路径、后清理。

### 阶段 A：逻辑下线
- 默认禁 workflow 主入口
- 日常任务走 mode + subagent

### 阶段 B：稳定验证
- 连续若干轮无锁死/无 resume 回归/无工具漂移

### 阶段 C：物理删除
- 删除 workflow 主链模块与命令
- 清理对应测试
- 保留 tag 便于追溯

---

## 9. 应急流程（简化版）

扩展异常时统一流程：
1. 禁用扩展
2. 重启 pi
3. 继续任务（原生能力）

> 本版不强制保留复杂扩展内自救命令，避免再次提升系统复杂度。

---

## 10. 迁移实施计划（可执行）

### P0：冻结高风险路径（1 天）
- 下线 message/history 改写
- 下线 workflow 默认入口
- 下线 fallback 魔法注入
- 固化 mode preset + 工具 allowlist

### P1：模式主路径上线（1-2 天）
- 打通 coordinator/fallback + subagent 主链
- 加入硬拦截（工具越权/伪执行/完成态）
- 保留 oracle 审查（格式+证据）

### P2：收尾清理（1-2 天）
- 删除 workflow 冗余代码（在 P1 稳定后）
- 降级 custom 事件渲染
- 清理失效测试与文档

---

## 11. 验收标准（必须量化）

### 稳定性
1. 连续多次 mode 切换无工具漂移
2. 新会话首轮工具集稳定可用
3. resume 不因扩展路径触发崩溃

### 约束有效性
4. 非 allowlist 工具 100% 被拦截
5. 伪执行（口头声明未执行）能被识别并拦截
6. 未满足完成态条件不能推进

### 质量
7. oracle 可拒绝“有格式无证据”的输出
8. 指令遵循与幻觉问题在主路径显著下降（人工抽检）

---

## 12. 风险与缓解

1. **风险：大删后短期功能回退**
   - 缓解：先下线后删除；保留分支和 tag。

2. **风险：模式主路径过于简化导致复杂任务效率下降**
   - 缓解：复杂任务阶段性人工分解，后续再按需恢复轻量编排。

3. **风险：团队习惯依赖 workflow**
   - 缓解：文档明确新主路径 + 一页迁移指南。

---

## 13. 需要同步到团队的关键口径

1. 我们不是“放弃质量约束”，而是把约束从提示词迁到系统硬门。
2. 我们不是“永远删除 workflow”，而是先下线主路径以恢复稳定性。
3. fallback 不再是救火机制，只是工作模式。
4. 扩展故障时，禁用扩展重启是标准兜底流程。

---

## 14. 与旧交接文档的关系

- 旧文档（Intent / tool / reset 三钩子）作为历史设计参考保留。
- 本文档覆盖并替代其默认执行路线：
  - 从“workflow + message_end 改写”转向“mode + runtime guard”。

---

## 15. 后续扩展原则（防止再复杂化）

新增任何功能前，必须回答：
1. 是否改写历史数据？（若是，默认拒绝）
2. 是否新增跨模块联动？（若是，必须给故障隔离方案）
3. 能否通过静态 preset + 硬门实现？（优先）
4. 是否可在禁用扩展后完全回退？（必须）

---

> 结论：
>
> 本次重构的核心不是“换一套更复杂机制”，而是把系统压缩回可控形态：
> **mode 主路径 + subagent 能力 + runtime 硬约束**。
> 先稳定，再增强。
