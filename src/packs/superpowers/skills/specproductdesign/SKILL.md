## 前置条件

- 有原始需求来源（聊天记录、表格、需求文档、口头描述）

## 核心流程

读取原始需求 → 讨论澄清 → 提出2-3种方案 → 呈现设计章节 → 用户批准 → 生成文档

## 关键原则

1. 一次只问一个问题 - 避免一次性抛出多个问题
2. 优先使用选择题 - 提供选项比开放式问题更容易回答
3. 功能设计不涉及实现 - 只说"做什么、长什么样"，不说"代码怎么写"
4. 增量验证 - 先呈现设计，获得批准后再生成文档
5. 保持灵活 - 当某些地方不合理时，愿意回头澄清

## 流程步骤

### Step 1: 读取原始需求

- 读取用户提供的聊天记录、表格、需求文档
- 如果是口头描述，让用户先完整描述

### Step 2: 讨论澄清

- 针对模糊的地方提问
- 确认产品目标、目标用户、核心功能

### Step 3: 提出2-3种方案

- 针对核心功能设计提出不同方案
- 说明每种方案的优缺点
- 让用户选择或融合

### Step 4: 呈现设计章节

逐个呈现以下章节，每呈现一个等待用户确认：

1. **产品概述** - 名称、一句话描述、目标用户、解决的问题
2. **用户角色** - 谁会使用这个产品
3. **用户旅程** - 主要使用流程
4. **功能需求** - 功能列表及详细设计
5. **技术选型** - 使用什么技术栈
6. **系统架构** - 简单架构描述

### Step 5: 用户批准

- 呈现完整设计摘要
- 用户确认批准

### Step 6: 生成文档

1. 确认项目名称（用于创建项目目录）
2. 生成固定格式的文档结构到 `docs/{project-name}/requirement/` 目录

## 输出格式

```
docs/{project-name}/
└── requirement/
    ├── index.md              ← 目录（跳转链接）
    ├── overview.md           ← 产品概述 + 用户角色 + 用户旅程
    ├── functions-01.md       ← FR01-FR10
    ├── functions-02.md       ← FR11-FR20
    ├── functions-03.md       ← FR21-FR30（如有）
    ├── tech.md               ← 技术选型 + 系统架构
    └── related-plans.md      ← 关联计划和进展（初始为空）
```

### index.md 模板

```markdown
# 需求设计文档 - {产品名称}

## 目录

- [产品概述](./overview.md#产品概述)
- [用户角色](./overview.md#用户角色)
- [用户旅程](./overview.md#用户旅程)
- [功能需求](./functions-01.md)
- [技术选型](./tech.md#技术选型)
- [系统架构](./tech.md#系统架构)
- [关联计划](./related-plans.md)
```

### overview.md 模板

```markdown
# 产品概述

{产品名称} - {一句话描述}

**目标用户：** {谁会使用}

**解决的问题：** {解决什么问题}

---

# 用户角色

{角色1}：{描述}

{角色2}：{描述}

---

# 用户旅程

{主要使用流程描述}
```

### functions-XX.md 模板

```markdown
# 功能需求

## FR01: {功能名称}

- {设计细节1}
- {设计细节2}
- {设计细节3}

## FR02: {功能名称}

- {设计细节1}
- {设计细节2}
```

### tech.md 模板

```markdown
# 技术选型

- 前端：{技术}
- 后端：{技术}
- 数据库：{技术}
- 其他：{如有}

---

# 系统架构

{架构描述或简单图示}
```

### related-plans.md 模板

```markdown
# 关联计划

> 此文档由 extract-tasks 技能自动维护，记录基于此需求设计文档生成的计划和进展。

<!-- 暂无关联计划 -->
```

## 唯一出口

文档生成到 `docs/{project-name}/requirement/` 目录后，技能结束。

**禁止：**
- 在功能需求中写实现细节（代码、API、数据结构）
- 跳过用户批准直接生成文档
- 生成非固定格式的文档
