## 前置条件

- 有需求来源：需求设计文档（`docs/{project-name}/requirement/`）或用户的想法描述

## 核心流程

探索项目上下文 → 提出澄清问题 → 提出2-3种方案 → 呈现设计章节 → 用户批准 → 模式选择 → 按模式执行对应流程

## 关键原则

1. 一次只问一个问题 - 避免一次性抛出多个问题让用户感到压力
2. 优先使用选择题 - 当可能时，提供选项比开放式问题更容易回答
3. YAGNI（你不会需要它） - 严格剔除设计中不必要的功能
4. 探索替代方案 - 在确定方案前，总是提出2-3种不同的方法
5. 增量验证 - 先呈现设计，获得批准后再继续
6. 保持灵活 - 当某些地方不合理时，愿意回头澄清

## 子 Agent 并行处理

当需要调查代码、搜索参考资料等操作时：

1. **派发多个子 agent 并行处理** - 不要主 agent 自己做
2. **独立任务同时派发** - 不相互依赖的任务同时运行
3. **等待结果汇总** - 系统通知完成后收集结果整合

**禁止：** 主 agent 直接做大量搜索/调查工作，浪费上下文

## 关联需求设计文档判断

### 判断逻辑
1. 检查上下文中是否引用了 `docs/{project-name}/requirement/` 的内容
2. 检查用户是否明确提到"需求设计文档"或相关文件
3. 根据讨论内容判断是否从需求设计文档出发

### 判断结果
- **是** - 标记 `requirementDoc: docs/{project-name}/requirement/`，传递给 writing-plans
- **否** - 不标记，传递空值
- **不确定** - 询问用户："是否关联到需求设计文档？"

## 模式选择门（mode_gate）

在用户批准设计后，选择执行模式：

1. **标准模式**：生成计划/任务文件，再实施（更稳）
2. **快速模式**：不写计划文件，直接用 TodoWrite 编排子代理实施并审查（更快，适合小改动）

> 选择：`标准模式` 或 `快速模式`（默认：标准模式）

### 分流规则

- 用户选择 `标准模式`（或未明确）→ **读取 `references/writing-plans.md`** 按步骤编写计划，然后执行 extract-tasks
- 用户选择 `快速模式` → **读取 `references/fast-track.md`** 按步骤执行，跳过计划文档

### 模式分流前的限制

在模式分流前，你**只允许**：
- 与用户对话（提问、呈现设计、获取批准、询问模式）
- 读取项目文件（了解上下文）
- 派发子 agent 并行处理调查任务

**禁止：** 在模式选择前进入实现阶段。

## 执行时的通用规范（两种模式共用）

无论哪种模式，在以下时机必须读取对应参考文档：

1. **计划编写时** → 读取 `references/writing-plans.md`
2. **任务拆解时** → 读取 `references/extract-tasks.md`
3. **每步实现前** → 读取 `references/tdd.md`，遵循 RED→GREEN→REFACTOR 的 TDD 流程
4. **在 specproductdesign 中写功能需求时** → 读取 `references/bdd.md`，按 GIVEN/WHEN/THEN 格式编写场景
5. **需要代码审查时** → 读取 `references/code-review.md`，按严重等级处理反馈
6. **子代理驱动执行时** → 读取 `references/subagent-workflow.md`
7. **批次执行时** → 读取 `references/executing-plans.md`
8. **完成开发时** → 读取 `references/finishing-branch.md`

## 设计交付物

- 设计确认后，进入模式选择
- 代码修改的声明协议（APPROVED/AWAITING_APPROVAL）由内置门禁自动处理，无需在对话中手动维护

## 唯一出口

模式选择确认后进入对应的执行流程。

**禁止：**
- 跳过用户批准直接实现
- 在功能需求中写实现细节（代码、API、数据结构）
- 跳过对应的参考文档直接凭记忆执行
